# 三维多无人机物流仿真系统后续改进计划书

## 1. 文档信息

- 项目：Multi-UAV Logistics Gazebo Simulation
- 主开发包：`logistics_gazebo_sim_ros`
- 稳定对照包：`logistics_gazebo_sim`
- 技术环境：ROS Noetic、PX4 SITL、MAVROS、Gazebo、OMPL、TOPPRA
- 当前基线：三架无人机物流任务，支持起飞、三维航迹、队形变换、投递、返航与降落
- 计划原则：先验证三维通行能力，再解除数量限制；先判断任务是否可行，再启动高成本仿真

## 2. 建设目标

将当前三机演示系统逐步升级为可配置数量、可根据三维通行空间自动调整队形、能够提前判断任务可行性并在失败时给出明确原因的多无人机物流仿真平台。

系统最终应具备：

1. 三维编队中心路径规划；
2. 包含高度变化的任意数量队形；
3. 根据水平和垂直净空自动选择队形；
4. 队形变换期间的机间与障碍物安全约束；
5. 多机轨迹时间同步与冲突消解；
6. 不可行任务的预检查、降级方案和明确报错；
7. 高保真PX4模式与大规模轻量算法测试模式；
8. 可重复构建、测试、回归和恢复的Git/GitHub流程。

## 3. 总体技术路线

```text
任务输入（场景、起终点、数量、高度、间距、偏好队形）
    ↓
场景三维占据模型与净空分析
    ↓
舰队容量及任务可行性预检查
    ↓
生成候选队形与队形包络
    ↓
OMPL规划编队中心三维路径
    ↓
沿路径选择队形及安全变换区域
    ↓
生成每架无人机的独立三维轨迹
    ↓
机间时空冲突检测与局部修正
    ↓
TOPPRA速度参数化与多机同步
    ↓
PX4/MAVROS跟踪、在线安全监控
    ↓
投递、返航、降落与任务报告
```

规划采用分层方法，不把全部无人机直接放入一个 `3N` 维联合状态空间。默认先规划编队中心，再生成单机轨迹，只对发生冲突的局部路段重新规划，以控制无人机数量提升后的计算复杂度。

## 4. 开发边界

### 4.1 稳定版本

`logistics_gazebo_sim` 作为当前可运行对照版本：

- 不进行大规模架构重构；
- 只修复影响演示、安全或恢复的严重问题；
- 用于与实验版进行效果和性能对比。

### 4.2 实验版本

`logistics_gazebo_sim_ros` 作为下一代主开发版本：

- 三维OMPL规划；
- 三维TOPPRA参数化；
- 高度方向队形与自动变换；
- 任意数量算法模型；
- 可行性分析、冲突检测与故障处理。

## 5. 分阶段实施方案

### 阶段0：固化当前基线

目标：确保任何后续改动都可以比较和恢复。

任务：

- 为当前稳定提交创建 `v0.1.0` 标签；
- 固化七个场景、三机配置和测试记录；
- 建立GitHub基础检查；
- 保存源码快照、Git bundle和依赖清单；
- 记录当前规划耗时、轨迹长度、最小机间距和任务完成时间。

验收：

- 两个ROS包独立构建成功；
- 三机完整任务可执行；
- GitHub和离线bundle均可克隆恢复；
- 工作区无未说明修改。

### 阶段1：三维净空与舰队容量分析

目标：在启动PX4和Gazebo任务前回答“能否通过”。

任务：

- 统一障碍物三维表示，支持盒体、柱体和世界边界；
- 计算路径局部水平净空、上方净空和下方净空；
- 根据数量、间距和队形计算三维编队包络；
- 检查起点容量、终点容量和投递展开空间；
- 输出可用队形、不可行路段及最大建议数量；
- 在UI显示原因和修改建议。

首批错误码：

- `E_START_CAPACITY`：起点无法安全容纳当前舰队；
- `E_GOAL_CAPACITY`：终点或投递区域空间不足；
- `E_CORRIDOR_TOO_NARROW`：水平净空不足；
- `E_VERTICAL_CLEARANCE`：垂直净空不足；
- `E_FLEET_CAPACITY`：当前约束下舰队规模不可行；
- `E_NO_FEASIBLE_FORMATION`：没有可通过全程的候选队形。

验收：

- 不启动仿真即可分析七个场景；
- 对明显不可行输入在限定时间内失败并给出具体原因；
- 可行性分析与实际三机仿真结果一致；
- 自动测试覆盖边界、高度和数量变化。

### 阶段2：独立三维队形管理器

目标：形成与无人机数量无关的队形算法层。

任务：

- 将队形生成、包络、槽位分配和过渡从任务播放器中拆分；
- 支持横向一字、纵向一字、垂直错层、三维楔形、网格和螺旋；
- 所有槽位使用 `(dx, dy, dz)`；
- 使用匈牙利算法进行槽位分配；
- 代价函数加入航程、交叉、爬升、原槽位保持和安全距离；
- 队形变换先生成候选轨迹，再进行连续碰撞检查。

验收：

- 1、3、5、8架均能生成合法队形；
- 队形内最小距离不低于配置值；
- 三机水平队形到垂直错层的全过程无碰撞；
- 相同输入结果可重复，并输出队形尺寸和分配代价。

### 阶段3：自动队形选择与高度变换

目标：让系统利用高度空间通过水平窄通道。

任务：

- 沿编队中心路径分段计算净空；
- 为每个路段评估候选队形；
- 在开阔区域搜索队形变换窗口；
- 将队形切换建模为受约束的三维过渡；
- 同时检查变换过程中的障碍物距离和机间距离；
- 通过狭窄区后恢复巡航队形；
- 保留用户偏好，但安全约束拥有更高优先级。

默认策略：

- 开阔区：三角形或三维楔形；
- 水平窄通道：纵向一字；
- 水平空间不足且垂直空间充足：垂直错层；
- 高度受限：平面紧凑队形；
- 投递区：一字队形；
- 返航：恢复巡航队形。

验收：

- 至少两个场景能自动触发高度方向变换；
- 变换位置不位于窄通道内部；
- 全任务最小机间距满足配置；
- 各单机轨迹与障碍物保持安全裕度；
- 无安全变换区域时明确拒绝任务。

### 阶段4：三维TOPPRA与多机时序协调

目标：使路径几何可行同时满足飞行速度和加速度约束。

任务：

- 分离水平、上升和下降速度限制；
- 分离水平和垂直加速度限制；
- 转弯、队形变换和载荷阶段自动降速；
- 同步队形变换的开始和结束时刻；
- 建立单机轨迹的时空冲突检测；
- 优先通过时间偏移解决冲突，必要时局部重规划。

验收：

- 所有采样点满足速度与加速度限制；
- 队形变换关键时刻同步；
- 无预测碰撞；
- TOPPRA失败时区分几何不可行与动力学不可行。

### 阶段5：解除三机硬编码

目标：在算法可行性得到验证后，再扩展PX4实例数量。

任务：

- 参数化PX4、MAVROS、端口和命名空间；
- 动态生成出生位置和控制节点；
- 安全监控、可视化、日志、UI及包裹管理使用统一车辆注册表；
- 单机异常隔离，不阻塞全部状态更新；
- 增加资源检查，启动前估计CPU、内存和端口占用。

验收顺序：

1. 单机冒烟测试；
2. 三机回归测试；
3. 五机完整任务；
4. 八机规划与分组任务；
5. 根据资源测试决定是否提高PX4实例数量。

不得只修改 `vehicle_count` 就启动更多实例。每个数量必须先通过阶段1的任务容量分析。

### 阶段6：分组与降级执行

目标：整体编队无法通过时仍能给出安全替代方案。

降级顺序：

1. 尝试用户偏好队形；
2. 尝试纵向一字；
3. 尝试垂直错层；
4. 减小队形但不突破最小安全距离；
5. 将舰队划分为多个小组；
6. 多组分时通过；
7. 所有方案失败后拒绝任务。

验收：

- 系统能够说明采用了哪一级降级；
- 分组之间满足空间或时间安全间隔；
- 不以压缩最小安全距离作为默认解决方案；
- 用户可以拒绝降级方案并修改任务参数。

### 阶段7：在线安全与重规划

目标：处理模型误差、跟踪误差和局部异常。

任务：

- 预测未来数秒的机间距离；
- 设置警告、减速、悬停、重规划和紧急降落等级；
- 检测失联、OFFBOARD失败、解锁失败和轨迹跟踪超差；
- 支持局部路径重规划；
- 记录安全事件和恢复过程。

验收：

- 预测冲突发生前触发处理；
- 单机异常不会造成其余无人机继续危险靠近；
- 每次安全事件都产生可复现日志；
- 安全状态能够在UI明确显示。

### 阶段8：可扩展UI与任务编辑

目标：让数量、队形和规划状态在界面中可理解、可操作。

任务：

- 动态生成车辆状态表；
- 支持地图点选起点、终点和中间航点；
- 显示候选路线、编队包络和队形变换区；
- 显示数量、间距、高度及队形可行性；
- 提供规划失败原因和修复建议；
- 任务保存、加载、重置和报告导出；
- 实时任务只保留只读进度，不提供伪快进。

## 6. 大规模仿真策略

提供两种运行模式：

### 高保真模式

- 每架无人机使用PX4 SITL和MAVROS；
- 用于控制器、通信、投递和降落验证；
- 规模受CPU、内存和实时性限制。

### 轻量算法模式

- 使用运动学或简化动力学模型；
- 用于20至50架的规划、队形和冲突压力测试；
- 通过后选择代表性规模进入PX4模式。

两种模式共享任务配置、队形算法、规划接口、日志格式和验收指标，避免形成两套不可比较的实现。

## 7. 参数与接口统一

建议统一舰队配置：

```yaml
fleet:
  vehicle_count: 3
  namespace_prefix: uav
  minimum_separation: 3.0
  spawn_spacing: 3.5
  execution_mode: px4

formation:
  preferred: wedge3d
  allow_automatic_switch: true
  allow_vertical_layers: true
  max_vertical_layers: 3

trajectory:
  horizontal_velocity: 2.0
  vertical_velocity_up: 0.8
  vertical_velocity_down: 0.6
  horizontal_acceleration: 1.0
  vertical_acceleration: 0.5
  sample_period: 0.1

planning:
  planner: informed_rrt_star
  solve_timeout: 3.0
  max_attempts: 3
  allow_grouping: true
```

所有节点从统一配置读取车辆数量和安全参数，禁止分别维护不同的三机常量。

- 记录成功率、耗时、最小间距、轨迹长度、最大速度和最大加速度。

## 9. Git与GitHub版本管理

### 分支

- `main`：已验证、可演示版本；
- `develop`：阶段集成；
- `feature/*`：单项功能；
- `fix/*`：缺陷修复；
- `release/*`：发布候选。

### 提交要求

- 每个提交只解决一个明确问题；
- 算法改变必须同时提交测试或测试记录；
- 不提交构建产物、缓存、飞行日志和密钥；
- 合入 `develop` 前完成快速测试；
- 合入 `main` 前完成规定的仿真回归；
- 每个稳定版本创建标签、发布说明和离线bundle。

建议版本：

- `v0.1.0`：当前三机基线；
- `v0.2.0`：三维净空分析与安全队形变换；
- `v0.3.0`：可配置数量、分组和时序协调；
- `v0.4.0`：在线安全与重规划；
- `v1.0.0`：稳定多机物流仿真平台。

## 10. 风险及控制措施

| 风险 | 控制措施 |
|---|---|
| 数量增加导致无路可走 | 先做容量和可行性预检查，支持分组与分时通过 |
| 队形变换时相撞 | 连续轨迹检测、槽位交叉惩罚、同步降速 |
| 高度变换碰撞建筑物 | 使用完整三维包络和上下净空约束 |
| OMPL偶发规划失败 | 多规划器候选、限定重试、区分超时与不可行 |
| TOPPRA求解失败 | 检查路径曲率和约束，允许安全范围内放宽时间而非距离 |
| PX4实例过多拖慢系统 | 资源预检查、高保真与轻量模式分离 |
| 仿真正常但实机不可实现 | 保留跟踪裕度，限制爬升率、加速度和控制频率 |
| 改动破坏稳定演示 | 稳定包冻结、功能分支、回归后合并、版本标签和bundle |

## 11. 近期执行顺序

近期不增加PX4无人机数量，先完成以下工作：

1. 给当前基线创建 `v0.1.0`；
2. 建立GitHub快速构建和算法测试；
3. 在实验版实现三维净空分析器；
4. 实现舰队容量及任务可行性预检查；
5. 将三维队形管理器从任务播放器中解耦；
6. 使用三机完成水平队形与垂直错层自动变换；
7. 完成变换全过程的障碍物与机间碰撞验证；
8. 完成七场景三机回归；
9. 再开始五机纯算法测试；
10. 五机算法可行后才启动五套PX4 SITL。

## 12. 阶段完成判定

只有同时满足以下条件，功能才可以从 `develop` 合入 `main`：

- 构建和自动测试通过；
- 指定场景完整仿真通过；
- 最小安全距离满足要求；
- 速度和加速度无越界；
- 失败输入有明确错误码和建议；
- 无未清理的PX4、MAVROS或Gazebo活动进程；
- 测试结果写入 `reference`；
- Git工作区干净且已生成恢复点。

本计划优先证明“三维高度变换确实提高通行能力”，再扩大无人机数量，避免将规模扩展建立在尚未验证的规划和队形机制之上。
